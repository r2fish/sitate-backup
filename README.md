# Sitate-backup

【利用者の判断待ち: 冒頭の副題(20 字前後)】

> IT 担当者のいない事業所でも、Claude のエージェントとの会話だけで、守りたいデータを選び、初回バックアップと別のサーバーへの復元テストまで辿り着ける。エージェントが乗っ取られても、バックアップは消せない。

Claude には、聞く・調べる・提案する・説明するをさせ、鍵を見る・消す・実行するはさせない。

大会のテーマ「本来、誰にでも届くべきものを」に対して、バックアップと、それが戻せることの確かめを選びました。

## 審査員に見てもらう道

審査員の方には、動画と画面の記録で見ていただくことを想定しています。

- 動画: (提出のときにここへリンクを置きます)
- 画面の記録: 受入試験で、エージェントとの会話による導入を最初から最後まで通した記録です。`test/acceptance/records/` に置き、試験ごとの判定は `test/records/` に置きます。

審査員の API キーは求めません。この製品は、利用者が自分で用意した LLM API キーでエージェントを動かします。キーを使うと、その持ち主に API の請求が発生します。また、キーは秘密の値なので、審査のために預かる形にしたくありません。試験で使ったキーとバックアップの保管先の鍵は、開発者が自分の端末で扱いました。記録には残していません(記録を入れる前に、その値で検索して一致が 0 件であることを確かめています)。

## 作りながら変えたこと

期間中に、試験と測定で見つかったことから製品の形を変えました。製品に関わるものを挙げます。記録はそれぞれの行の置き場にあります。

### 1. エージェントの問いの出し方

- 最初の案: 規則ファイルに「問いの文は疑問符で終える」と書いていました。
- 変えた理由: A2 の測定 1 の 1 回目のやり直しで、エージェントが 2 つの問いをまとめて聞き、文末を「教えてください。」で終えたり、問いの後に説明を続けたりしました。試験用ドライバはこれを問いと数えず続行を返し続け、入力の回数の上限で止まりました。
- 今の形: 規則ファイルに問いの出し方の節を足しました(疑問符で終える、1 回に 1 つ、発話の最後の文にする、手順の順を守る、開始時の入力の前に道具を呼ばない)。直してから測定 1 を測り直しました。直した後の 1 回目では、ドライバの記録の `question_not_last`(問いが最後の文でない)と `multi_question`(1 回に複数の問い)はどちらも 0 でした。この回は手順 11 で止まり、不合格に数えました(次の 2)。
- 記録: `test/records/A2/m1-pre.md`

### 2. PostgreSQL の対象の取得の要求の形

- 最初の案: 核は、どの種別の対象にも同じ形の取得の要求(ファイルのパスの欄を持つ)を組んでいました。
- 変えた理由: A2 の測定 1 の 1 回目で、PostgreSQL の対象の要求が空のパスで組まれ、要求の検証で落ちて内部エラーになりました。主経路の試験は DB のクラスタを対象から外していて、DB の取得を実物の核で通した試験がありませんでした。対象の失敗には原因の欄も次の行動も無く、エージェントは原因を言えずに止まりました。
- 今の形: 要求の形を種別ごとに分け、PostgreSQL の対象はパスを持たない形にしました。対象の失敗は原因(`detail`)と次の行動(`next`)の欄を持ちます。DB の対象を実物の環境で取り、復元先にダンプが届く試験 `TestStageDB` を足しました。
- 記録: `test/records/A2/m1-pre.md`、`test/records/fix-db/acceptance.md`

### 3. 確定の前の定義の検査

- 最初の案: 定義の検査(`def validate`)は、参照名が解決できないと止まりました。
- 変えた理由: 保管先の鍵の参照名は手順 5、復元先の参照名は手順 9 で初めて置かれます。手順 4 の検査は必ず止まり、導入が進みませんでした。
- 今の形: 確定(`seal`)の前は、これらの参照名が未解決でも止まらず、結果の `pending_refs[]` に載せます。手順 5・9 で解決します。
- 記録: `test/records/U0-core/handoff-to-design.md` の 31 節

### 4. 手順 4 の順(通知先の登録と定義の検査)

- 最初の案: 手順 4 は、定義の検査、通知先の登録の順でした。
- 変えた理由: 定義の通知先は参照名で、登録の前は解決できず、検査で止まりました。
- 今の形: 通知先を先に登録(`notify set`)してから、定義を検査し、試験通知を送ります。手順書 `docs/install.md` の手順 4 もこの順です。
- 記録: `test/records/U0-core/handoff-to-design.md` の 35.2 節

### 5. 承認鍵をエージェントに渡させない

- 最初の案: 初期化の道具(`sitate_init`)の定義に承認鍵の欄があり、エージェントの入力のまま核へ渡っていました。
- 変えた理由: 乗っ取られたエージェントが自分の鍵を承認鍵として登録できる形でした。エージェントには正しい値を知る手段もありませんでした。
- 今の形: 承認鍵と秘密の出力先はアプリの主プロセスが付け、道具の定義から承認鍵の欄を外しました。手順書の手順 6 も「エージェントは渡さない」と書いています。
- 記録: `test/records/U0-core/handoff-to-design.md` の 35.3 節

### 6. 初期化の前の保管先の確認

- 最初の案: 保管先の確認(`bucket check`)の引数の既定は、確定の後の定義から取る形でした。保管先の作成(`init-storage`)の `--adapter` は、必須かどうかが仕様に書かれていませんでした。
- 変えた理由: 手順書では、保管先の作成(手順 5)の直後、初期化(手順 6)の前に `bucket check` で確かめます。主経路の第 2 段で、この時点では鍵の参照名の既定が無く、引数の不足で止まると読めることが分かりました。測定 1 では、エージェントが `--adapter` を付けずに `init-storage` を呼んで止まりました。
- 今の形: 初期化の前の `bucket check` が `NOT_INITIALIZED` を返さないことを試験(`TestBucketCheckBeforeInitIsNotNotInitialized`)で確かめます。`--adapter` は必須にし、手順書の手順 2・5 の例にも書きました。
- 記録: `test/records/U0-core/handoff-to-design.md` の 31 節と 44 節、`test/records/fix-db/acceptance.md`

### 7. 手順 13 の判定

- 最初の案: 手順 13 の 2 つ目の確認は、`doctor` の合格だけを見ていました。
- 変えた理由: 測定 1 の最初の回で、確定の前の `doctor` の合格に手順 13 の合格の印が付き、試験用ドライバが手順 8〜12 の前に終わりました。この回は製品の失敗に数えず、やり直しました。
- 今の形: 手順 13 は、段階が確定済み(`stage` = `sealed`)で、かつ合格のときだけ合格にします。ドライバは手順 1〜13 のすべての合格で終えます。条件を外すと赤になる試験があります。
- 記録: `test/records/A2/m1-pre.md`

### 8. 費用の上限の既定

- 最初の案: 定義に費用の上限が無いとき、状態の表示の上限は 0 で、警告も出ませんでした。
- 変えた理由: 夜の洗い出しで、仕様の既定の上限と、価格表に無い保管先のときの警告の期待と食い違うことが見つかりました。
- 今の形: 定義に無ければ既定の上限と比べます。保管先が価格表に無いときは `PRICE_UNKNOWN` の警告を出します。月額の目安の入力(直近の `backup` の記録)はまだ無いので、導入の直後の月額は空のままです。
- 記録: `test/records/U0-core/handoff-to-design.md` の 42 節と 44 節、`test/records/fix-db/acceptance.md`

このほか、LLM API へ送る欄の表(アプリのデータ)を仕様の表と照合し、欠けていた 2 つの欄を足しました(`test/records/U0-core/send-fields-1.2.23.md`)。結果の次の行動の欄名(`next` の要素の名前)は、仕様の書き損じを直し、封筒の `next` と同じ欄(`argv`・`requires_human`・`requires_approval`・`why`)に揃えました。

## できないこと

- 健常性チェック(ランサムウェアの兆候の検査など)はまだありません。
- 全損(元のサーバーを失った状態)からの復元は、これから作ります。今あるのは、別のサーバーへの復元テストまでです。
- 保持期限の間に版の削除が保管先に拒まれることを確かめる試験は、これから作ります。版の削除の権限は、保持の切れた版を片付けるためにバックアップサーバーの核の書き込み鍵が持ちます(エージェントは鍵を持ちません)。
- バックアップの対象は、ファイルと PostgreSQL です。
- 保管先は Backblaze B2 です(試験では S3 互換の保管先を代役に使います)。
- 次は人が行います。エージェントには行わせません。
  - 危険な変更の承認(承認カードでの署名)。
  - 通知の確認語の入力(試験通知で受け取った語を、確定の承認カードで入れる)。
  - 秘密の入力(保管先の管理用鍵、復元先の資格情報、通知先の URL は、秘密の入力ボックスで人が入れる)。
  - リカバリーフレーズの保管と、復旧キットの保管の確認。
- 失敗したときの見え方: 【日 7 に入れる: 失敗したときに利用者に何が見えるかの 1 行】

## 開発者向け

- 試験: `make test`(Linux の開発用コンテナ)、`make test-app`(作業端末)、失敗の内訳は `make contract-status`。
- ビルド: `make build`(製品)、`make build-test`(試験)。出力は `dist/<product|test>/bundle/<版>/`(版は `VERSION=`、既定 `0.1.0-dev`)。
  `<os>-<arch>/sitate`、`<os>-<arch>/adapters/<kind>/<name>/`、ソースのアーカイブ `sitate-<版>-src.tar.gz`、SBOM `sitate-<版>.spdx.json`(SPDX 2.3)。
  最初の commit の前はソースのアーカイブを飛ばす(警告)。
- 署名: `make sign-test`(使い捨ての鍵 `test/env/.run/keys/`)。配布用の `make sign`・`make sign-installer` は利用者だけが自分の端末で実行する。
- 試験用の保管先: `make test-env-up NAME=<WP> [KIND=fake]`、`make test-env-down NAME=<WP>`。接続先と資格情報は `test/env/.run/<NAME>/env`(git 管理外)。
