# Sitate-backup

**IT 担当のいない職場のための、会話で始められて、戻せることまで確かめるバックアップ**

> Claude のエージェントとの会話で、守りたいデータを選び、初回バックアップと別のサーバーへの復元テストまで進める。エージェントが乗っ取られても、バックアップは消せない。

**できること**

| | |
|---|---|
| 会話で始める | 管理者の端末のアプリで Claude と話しながら、守りたいフォルダと PostgreSQL のデータベースを選んで導入します。サーバーの調べと設定の案は Claude が出し、危険な変更は人が承認カードで決めます |
| 毎日取る | バックアップサーバーが毎日 2 時 30 分(日本時間)に取り、暗号化してから保管先(Backblaze B2)へ送ります。保管先には、保持期限まで誰も消せない設定(Compliance モードのロック)で書きます |
| 戻せることを確かめる | バックアップの後に、別のサーバー(復元先)へ実際に戻し、記録と一致するかを照らします。結果はアプリの「状態と報告」に ✓ / ✗ で出て、失敗は通知で知らせます |
| AI に消させない | Claude がするのは、調べることと案を出すことまでです。危険な変更は人の承認なしには起きず、保管先・サーバーの鍵と承認鍵の値を Claude は見ません。乗っ取られたエージェントを想定した受入試験 A6 は、合格 20・不合格 0(未実行 2) |

動画と、試験の結果の置き場は、下の「審査員に見てもらう道」にあります。

Claude には、聞く・調べる・提案する・説明するをさせます。鍵を見る・消す・実行するは、仕組みとしてさせません。

大会のテーマ「本来、誰にでも届くべきものを」に対して、バックアップと、それが戻せることの確かめを選びました。達成できたのは、その核です。会話で導入から最初のバックアップと復元テストまで進むことは、提出日に R2-san の VPS で確かめました。一方で、導入の前の環境設定(サーバーの権限とファイアウォール、DB の権限など)には、まだ IT の知識が要ります。この日も 5 か所を人が手で直しました(下の「できないことと、これから」)。IT の知識の無い人には、まだ届いていません。エージェントが環境設定を助言できるように更新していきます。

私は障がい者支援施設の支援職員で、IT 担当ではありません。職員約 50 名が使う職場の業務アプリを Claude Code で作り、VPS で運用しています。職員が携帯から出す申請は、アプリの DB にしかありません。最初は、バックアップは取れば済むと思っていました。ランサムウェアでデータを取り出せなくなったニュースを見て、取るだけでは済まないと考えました。この危機感が、このプロジェクトの動機です。

## 審査員に見てもらう道

審査員の方には、動画と画面の記録で見ていただくことを想定しています。

- 動画: https://youtu.be/myoJiRsx8GY (YouTube の限定公開。179 秒)。製品を映す場面は、受入試験と同じ試験ビルドと合成データの環境で録りました。
  - アプリの入力とクリックは、受入試験の自動の操作役(ドライバ)が入れたもので、人の手の速さではありません。待ち時間は編集で切っています。
  - エージェントの応答は、実物の LLM のものです(LLM へはドライバの中継を通して送ります)。
  - サーバーはすべて作業端末の上のコンテナです。通知の受け手も試験のコンテナで、実物のメールやチャットではありません。危険な操作を拒む場面の保管先は、B2 ではなく試験用の S3 互換の保管先です。
  - 試験ビルドは、使い捨ての署名鍵、試験の時計、接続先の読み替え(試験の環境のコンテナに届くため)を使います。
  - リカバリーフレーズの語は、使い捨ての環境のものですが、ぼかしています。
- ドライバの記録: 受入試験で、エージェントとの会話による導入を最初から最後まで通した記録(会話・道具の呼び出し・結果の JSONL)です。公開用に縮めて識別子を伏せ字にしたものを `test/acceptance/records/` に置き(縮め方は `test/records/A7/shrink-2026-11-05.md`)、試験ごとの判定は `test/records/` に置きます。

審査員の API キーは求めません。この製品は、利用者が自分で用意した LLM API キーでエージェントを動かします。キーを使うと、その持ち主に API の請求が発生します。また、キーは秘密の値なので、審査のために預かる形にしたくありません。試験で使ったキーとバックアップの保管先の鍵は、開発者が自分の端末で扱いました。記録には残していません(記録を入れる前に、その値で検索して一致が 0 件であることを確かめています)。

## できないことと、これから

日付は約束しません。埋めた行も、埋めたことを書いて残します。

| いまできないこと | 何で埋めるか |
|---|---|
| 健常性チェック(ランサムウェアの兆候の検査など)はまだありません | 次のイテレーションで作り、受入試験で確かめます |
| 元サーバーを失ったときに、データを別のホストへ戻して使えるようにする復元は、まだできません。今あるのは、隔離した復元先へ戻して元と照合し、その後に破棄する復元テストまでです | 次のイテレーションで作り、受入試験で確かめます |
| 全損(バックアップサーバーも失った状態)からの復元も、まだできません | 次のイテレーションで作り、受入試験で確かめます |
| 保持期限の間に版の削除が保管先に拒まれることを、まだ試験で確かめていません。版の削除の権限は、保持の切れた版を片付けるためにバックアップサーバーの核の書き込み鍵が持ちます(エージェントは鍵を持ちません) | その次のイテレーションで、保管先が削除を拒むことを受入試験で確かめます |
| 元サーバーのファイルを読むために、読み取り専用の利用者に ACL を付けます。その副作用で、アプリの umask が効かなくなって新しいファイルが他者に読める場合があり、既存のファイルの群のビットが ACL の mask に変わります(0600 が 0640 として記録・復元される)。どちらも試験で確かめました(`test/records/U0-core/handoff-to-design.md` の 18 節) | ACL を付けずに読む受け口を作ります |
| 電子メールでの通知はまだありません | 通知のアダプタを足します |
| バックアップの対象は、ファイルと PostgreSQL です | 取得のアダプタを足して広げます |
| 保管先は Backblaze B2 です(試験では S3 互換の保管先を代役に使います) | 保管先のアダプタを足して広げます |
| 期間中にできた製品で、長い運用の実績はまだありません | R2-san の職場の業務アプリの DB で運用を始め、復元テストの合格記録を積みます |
| 保管形式(チャンク化・暗号・マニフェスト)は自作で、確かめたのは自動試験と、別に起動した AI のレビューまでです | 第三者による確認を受けます(時期は未定) |
| 大きいデータ・長い期間・多数の世代での性能と容量は、製品ではまだ測っていません | 測る項目と測り方は決めてあり、運用の中で測ります |
| 核の対応 OS は Linux(x86_64・arm64)で、確かめた構成は 1 組(保管先 B2・復元先 `ssh-host`)です。導入(`bootstrap`)が受けるサーバーは Debian と Ubuntu(とそれを元にした OS)だけで、root か、パスワードを問わない sudo が要ります。管理者端末(アプリ)は macOS だけです | 構成を足すたびに、同じ受入試験で確かめます |
| 状態と週の報告の「バックアップされていない場所」の数(`uncovered_count`)と、適用を待つ変更の数(`pending_changes`)は、まだ常に 0 です。アプリの状態の画面の「バックアップされていない場所」の行も、常に 0 と出ます。取得のときの判定はありますが、状態と報告に繋いでいません | 判定の結果を状態と報告に繋ぎます |
| 鍵の更新(`key-rotate`)とリカバリーフレーズの再発行(`phrase-reissue`)は、まだできません(`NOT_IMPLEMENTED`)。アプリの案内の 1 文(秘密の入力ボックスに入れたフレーズは、鍵の更新を提案して替える)は、この未実装の操作を勧めています | 鍵の更新を作り、案内と揃えます |
| 承認鍵は管理者端末のキーチェーンにだけあり、書き出す道がありません。管理者端末を失うと、危険な変更を承認できなくなります | 承認鍵を別の端末へ移す道を作ります |
| 導入の前に「バックアップサーバーの接続先」を登録したときと、先に話しかけたときは、チャット欄の「始める」ボタンが出ません(そのまま打って始められます) | 案内を出す条件を見直します |
| 製品ビルドで実際のサーバーへ導入して通したのは 1 組だけです(上の R2-san の VPS)。その中で欠陥が 1 つ見つかりました。復元先が ECDSA のホスト鍵を持っていると、手順 9(復元先の登録)が `RESTORE_HOSTKEY_MISMATCH` で止まります。復元先のアダプタは Ed25519 の鍵で指紋を固定し(`adapters/restore-dest/ssh-host/conn.go`)、続けて核が復元先へつなぐ接続は鍵の種類を指定せず ECDSA を先に選ぶためです(`internal/cli/ssh.go`)。試験の環境の復元先は Ed25519 の鍵しか持たず、試験では見つかりませんでした。今回は、復元先の sshd に `HostKeyAlgorithms ssh-ed25519` を置いて通しました。この設定は手順 3 の前に置いてください(手順 3 の隔離の後は、事業者のコンソールからしか入れません) | イテレーション 2 で、復元先への接続の鍵の種類を Ed25519 に揃えます。試験の環境の復元先に ECDSA の鍵を足し、直す前に赤になることを確かめてから直します |
| バックアップの核(取得・保管・別のサーバーへの復元テスト)は、実機で通りました。一方で、導入の前の環境設定は、まだ IT の知識が要ります。提出日の実機の通しでは、製品のエージェントとの会話だけでは進めず、人が端末や事業者のコンソールで手を入れた所が 5 つありました。元サーバーへの `acl` の導入と一時的なパスワードなしの sudo、元サーバーのファイアウォールでバックアップサーバーからの SSH を許すこと、DB に読み取り用の役割の接続の権限を与えること(手順 8)、通知の受け口を自分で用意すること、復元先のホスト鍵の欠陥の回避(上の行)です。どれも、別に開いた Claude Code の助けで進めました。IT 担当のいない職場が 1 人で辿り着ける状態には、まだなっていません | IT の知識の無い人が導入できるように、エージェントが環境設定(元サーバーの権限とファイアウォール、DB の権限、通知の受け口、復元先の鍵)を助言できるように更新していきます。同じ実機で通し直し、人が手を入れた所の数を数えます |
| イテレーション 1 はインストーラーを配りません。アプリはリポジトリから組んで起動します(下の「始め方」。R2-san の署名を付けた製品ビルドは `make build-app`、誰でも組めるのは試験ビルド) | アプリの配り方(インストーラーの形、OS のコード署名と公証)は次のイテレーションで決めます |
| 復元テストは毎日走ります。仕様の「同じ月に合格済みなら実行しない」判定がまだ無く、導入の確定(seal)の後は、タイマーが毎日、保管先から全量を読み出して復元先で復元テストを行います | イテレーション 2 の最初の作業で月の判定を入れ、35 模擬日で実行が 2 回になることを数える試験を足します |
| 保管先からの読み出し量の上限と、上限を超える読み出しを人に承認させる仕組みは、まだありません。タイマーとエージェントからの復元テストの読み出しは、承認なしで行われます | 読み出し量の累計と予約は、イテレーション 3 で入れます |

同梱の手順書と説明書(`docs/install.md`・`assets/manual/manual.md`)は復元テストを「毎月」と書いていますが、このビルドは毎日行います(上の表)。手順書と説明書は署名した同梱物で、受入試験のエージェントの入力なので、測ったものから変えていません。動画に映るエージェントの「毎月の復元テスト」も同じです。

次は人が行います。エージェントには行わせません。

- 危険な変更の承認(承認カードでの署名)。
- 通知の確認語の入力(試験通知で受け取った語を、確定の承認カードで入れる)。
- 秘密の入力(保管先の管理用鍵、復元先の資格情報、通知先の URL は、秘密の入力ボックスで人が入れる)。
- リカバリーフレーズの保管と、復旧キットの保管の確認。

失敗したときの見え方: バックアップか復元テストが失敗すると、通知先へ `backup.failed` か `restore_test.failed` の通知が届き、アプリの「状態と報告」のその行が ✗ になります。アプリを開いたままのときは、その行に「AI に見立てを聞く」のボタンが出て、押すと Claude が状況と次にすることを説明します。アプリが状態を読み直したときに、バックアップが 2 日より前から無いことなどに気づくと、OS の通知でも知らせます(ユーザーガイド 5.3・6 章)。

設計の起草も実装もレビューも Claude が行う 1 人の開発で、R2-san は基準(緑を信じない、測った値だけを書く、できないことを書く、決めるのは人)と採否を持ち、Claude がその基準を満たす仕組みを形にしました。その上で、仕様と脅威の一覧と自動試験を持つバックアップ製品を、期間中に実装しました。

### 精度の出し方

次の 5 つは最初からあった設計ではなく、失敗のたびに足していったものです。足すかどうかを決めたのは人、形にしたのは Claude です。

1. **役割を別の起動に分け、実装とレビューは別のモデルにする。** 起草とレビュー、実装とレビュー、レビューと監査は必ず別の起動にしました。実装は sonnet、レビューは opus です(起草とレビューはどちらも opus で、起動が別です)。同じ文脈で書いて点検すると、同じ思い込みで通るためです。
2. **「絶対に」の規則は指示でなくフックにする。** 例外を許さない規則は、人と AI の注意に任せず、フックが機械的に拒む形にしました(拒むものは下の機能の表)。
3. **緑を証拠にしない。** 規則として、承認・秘密・送信の制限などの規則の試験は、規則を 1 か所壊した変異で赤になることを確かめてから完了にし、欠陥の修正は修正前のコードで新しい試験が落ちた記録を残し、skip を合格に数えず、既知の欠陥は試験を消さずに赤のまま残して理由を書く、と定めました。実際に行った範囲: 変異に触れた記録は、WP ごとの受け入れの記録の置き場 21 のうち 19 にあります。変異の件数と生き残った件数は記録ごとに書き方がそろっておらず、合計は取れませんでした。例は `test/records/U3a/acceptance.md`(規則を壊す変異 19 件のうち 18 件が赤。生き残りの 1 件は理由とともに記録)と、`test/records/fix-db/acceptance.md` の「監督の再実行と変異」です。修正前の赤の記録は一部の WP だけで、変異で代えた WP もあります。
4. **文書どうしの食い違いを機械で落とす。** 設計の文書(このリポジトリの外。公開していません)を直すたびに、1 か所を直しても同じことを言う他の場所が古いまま残る食い違いが続いたので、R2-san が求め、Claude が commit の前に機械で落とす検査を書きました。その後、過去の指摘(期間前に採った 1,070 件)を分類すると、この型が 374 件で最も多く、分類をもとに検査を 3 つ足し、レビューの点検表も分類から作りました。
5. **決めたことを追記だけで残し、採らなかった案も書く。** 決定記録は番号付きの追記だけで、覆すときは新しい番号を起こします。期間中は監督を設計と製品の 2 つのセッションに分けました。製品の監督が実装で見つけた仕様の食い違いを申し送り(`test/records/U0-core/handoff-to-design.md`)に書いて設計の監督へ知らせ(初日は R2-san が貼って運び、2 日目からはセッションどうしが直接知らせる)、設計の監督が裁定して仕様書の版を上げ、製品の監督へ写しました。裁定には、前に別起動のレビューを通したもの、急ぐので機械の検査だけで返して後からまとめてレビューを通したもの、機械の検査だけのものがあります(数は上の表)。

### 報告を信じさせない

- 証拠: 実装担当の報告もレビューの結論も証拠にしません。証拠は、試験ログの集計行の逐語、ログの日時と `git diff --stat` の一致、差分、実測の記録だけです。完了の報告は、完了条件ごとの試験の名前、試験の結果の逐語、修正前のコードでの赤の記録、変異の記録、確かめていない項目の一覧、の 5 つの形で出させます。「全件通った」だけの報告は受け付けず、走らせられなかった試験は「未検証」と書かせます。
- レビュー: ログの日時・`git diff --stat`・試験の結果の逐語で確かめさせ、推論だけで「直った」と結論させません。報告は「確認した観点」と「していない観点」を別の節に分け、赤は 1 件ずつ分類させます。設計の文書のレビューには、過去の指摘の分類から起こした点検表 10 項目を使い、項目ごとに確かめた範囲と確かめていない範囲を報告させます。
- 監査: 完了条件ごとに充足・未充足・証拠不足の 3 値で判定させ、証拠不足を充足に数えません。最終の判定は、監督が最終の作業ツリーで試験を自分で 1 回流し直してから行います(WP ごとの受け入れで行い、全体の受け入れ監査は 7 日目)。
- 実例(測った値): 監査の予行(3 日目)では、完了条件 300 件を充足 117・未充足 20・証拠不足 143・範囲外 20 に分けました。証拠不足の多く(104 件)は完了条件と試験名の対応表の欠けで、7 日目の監査で初めて穴が見つかることを避けるための予行です(`test/records/schedule/day3-midpoint-2026-11-04.md`)。契約の骨格を相手にした契約試験では、判定の行 494 行のうち失敗より手前で実行が届いたのは 8 行(1.6%)で、骨格での赤は試験の品質の根拠にならないと分かり、主経路を先に通す形に変えました(`test/records/U0-core/acceptance.md`)。
- 設計の側: 期間前から、このリポジトリの外で、独立レビューの記録 104 本、決定記録 232 件(うち期間中は D-0152 以降の 81 件。2026-11-08 時点)を残しました。

## 作りながら変えたこと

期間中に、試験と測定で見つかったことから製品の形を変えました。製品に関わるものを挙げます。記録はそれぞれの行の置き場にあります。

### 1. エージェントの問いの出し方

- 最初の案: 規則ファイルに「問いの文は疑問符で終える」と書いていました。
- 変えた理由: A2 の測定 1 の 1 回目のやり直しで、エージェントが 2 つの問いをまとめて聞き、文末を「教えてください。」で終えたり、問いの後に説明を続けたりしました。試験用ドライバはこれを問いと数えず続行を返し続け、入力の回数の上限で止まりました。
- 今の形: 規則ファイルに問いの出し方の節を足しました(疑問符で終える、1 回に 1 つ、発話の最後の文にする、手順の順を守る、開始時の入力の前に道具を呼ばない)。直してから測定 1 を測り直しました。直した後の 1 回目では、ドライバの記録の `question_not_last`(問いが最後の文でない)と `multi_question`(1 回に複数の問い)はどちらも 0 でした。この回は手順 11 で止まり、不合格に数えました(次の 2)。
- 記録: `test/records/A2/m1-pre.md`

### 2. PostgreSQL の対象の取得の要求の形

- 最初の案: 核は、どの種別の対象にも同じ形の取得の要求(ファイルのパスの欄を持つ)を組んでいました。
- 変えた理由: A2 の測定 1 の 1 回目で、PostgreSQL の対象の要求が空のパスで組まれ、要求の検証で落ちて内部エラーになりました。主経路の試験は DB のクラスタを対象から外していて、DB の取得を実物の核で通した試験がありませんでした。対象の失敗には原因の欄も次の行動も無く、エージェントは原因を言えずに止まりました。
- 今の形: 要求の形を種別ごとに分け、PostgreSQL の対象はパスを持たない形にしました。対象の失敗は原因(`detail`)と次の行動(`next`)の欄を持ちます。DB の対象を実物の環境で取り、復元先にダンプが届く試験 `TestStageDB` を足しました。
- 記録: `test/records/A2/m1-pre.md`、`test/records/fix-db/acceptance.md`

## 無料で自前に組むツールと比べて

比べる相手は、無料で自前に組むツール(restic・BorgBackup・Kopia)に限ります。相手の欄は 2026 年 10 月の調査です。比較の条件(対象・保持・支援の範囲)が揃わないので、事実だけを並べます。導入の手順の数は数え方が違うので並べません。この製品の欄は、受入試験で確かめたものだけです。

| 項目 | 無料で自前に組むツール(2026 年 10 月の調査) | この製品(確かめた試験) |
|---|---|---|
| 戻せることの確認 | 別のサーバーへ戻して確かめる復元テストは、3 つとも手で行う。復元を証明する仕組みは、restic は調べた範囲で見つからず、BorgBackup(borgmatic)は部分的(展開のドライラン、元ファイルとの比較)、Kopia は部分的(構造と存在の確認) | 別のサーバーへ実際に戻して確かめ、署名した合格の記録を出す(A2 の手順 12)。定期の実行と世代の整理のタイマーは、導入の会話の中で登録される(A2 の手順 13 の `doctor` の `timers_registered`) |

この製品は、導入と運用の会話を AI のエージェントに任せる作りです。比べた 3 つのツールの調査では、この点は項目にしていません。危険な変更が人の承認を経ないと起きないこと(遅延のある操作は時間の遅れも経ること)は A6、秘密の値がモデルに送られないことは A7 で確かめました。

## 始め方(リポジトリから組んで、アプリを起動するまで)

開発者向けの節です。審査には要りません(審査員の API キーは求めません。上の「審査員に見てもらう道」)。

### 要るもの

- macOS の作業端末。アプリの起動を確かめたのは macOS だけで、Windows と Linux の作業端末では確かめていません。
- Docker。核とアダプタは Linux の開発用コンテナの中で組みます。Go(1.26)と minisign はコンテナの中にあり、作業端末には要りません。
- Node.js 22.18 以上と npm。
- 製品ビルドの署名(`make sign`)を行う人だけ、作業端末に minisign。

### 組んで起動する(試験ビルド)

誰でも組めるのは、使い捨ての鍵で署名する試験ビルドです。リポジトリの根で次を順に流します。

```
npm --prefix app ci
node app/node_modules/electron/install.js
make build-test
make sign-test
make build-app-test
cd app && npx electron .
```

- 2 行目は Electron の実行体を入れます。npm 11 では依存の導入スクリプトが既定で止まり、`npm ci` の後に実行体がありませんでした。
- 出来上がる物: 核・アダプタ・価格表は `dist/test/bundle/<版>/`、アプリは `app/dist/`。使い捨ての鍵は `test/env/.run/keys/` に作られます(リポジトリに入りません)。
- 試験ビルドは受入試験の環境のためのものです。試験の時計と、接続先の読み替え(試験の環境のコンテナに届くため)を持つので、実際のサーバーには使いません。

### 製品ビルド

```
make build
SECRET_KEY=<秘密鍵の絶対パス> PUBLIC_KEY_FILE=<公開鍵の絶対パス> make sign
PUBLIC_KEY_FILE=<公開鍵の絶対パス> make build-app
```

- `make sign` は配布用の秘密鍵で署名します。秘密鍵は R2-san の端末だけにあり、リポジトリの外から渡します。アプリは同梱物の署名を、組み込んだ公開鍵で確かめます。署名の無い同梱物があると `make build-app` が止まります。
- 自分で作った minisign の鍵の組でも同じ手順で組めますが、それは R2-san の署名ではありません。

### その先

- 製品ビルドのアプリなら、導入手順書 [`docs/install.md`](docs/install.md) の「開始前に用意するもの」から進みます。
- 試験ビルドのアプリで流れを試すなら、手順書へは進まず、受入試験の環境(`test/env/`)に向けて使います。入口は [`test/acceptance/launch.md`](test/acceptance/launch.md) です。

- 流して終了 0: `npm --prefix app ci`、`node app/node_modules/electron/install.js`、`make build-test`(`make sign-test` は 59 件に署名)、`make build-app-test`、`make build`。
- `cd app && npx electron .` で試験ビルドのアプリを起動し、8 秒後もプロセスが動いていることを確かめました。画面の中身は見ていません。

LLM API キーは、エージェントのプロセスが持ちます(起動の後に渡されます)。「鍵を見せない」と言うのは、保管先・サーバーの鍵と承認鍵の値がモデルの文脈に入らないことです。

エージェントが核の結果の値(原因コード・日付・大きさ・金額・件数など)を述べるときは、`[[<サブコマンド>:<JSON Pointer>=<値>]]` の印を付けさせ、アプリがその会話の最後の結果と照らします(引用の照合。`app/src/main/quote-check.ts`)。合わない印や、印の無い値の主張がある応答は、人に見せずに止め、エージェントに知らせます。提出するビルドの測定 4 では、3 回とも、人に見せずに止めた応答が 1 件ずつありました。3 回目の例では、手順 2 の結果を述べた応答の印の 1 つ(`init-storage` の結果の `/result/plan/errors`)が照合に通らず、その応答は表示されませんでした。エージェントは次の応答で「直前の私の応答は、引用の照合に通らず、表示されませんでした。」と述べ、その値を引用せずに述べ直しました(`test/records/A2/m4-3-questions-observe.md` の 2 と「再試行・エラー」の行)。

提出するビルド(測定 4 と同じ試験ビルド)の A6 は、CLI の回を受入試験の環境で流し直して合格し(`TestA6CLI`)、静的検査も合格し、実物の LLM の注入文の回と合わせた判定は `A6 summary PASS=20 FAIL=0 UNRUN=2` です(`test/records/A6/real-m4-2026-11-05.md`)。前のビルドの値: CLI の回は、測定 3 より前のビルドで、実物の LLM API と保管先には何も送らない試験ビルドと受入試験の環境で行い、12 項目が合格しました(`test/records/A6/cli-2026-11-04.md` の集計行 `A6 summary PASS=12 FAIL=0 UNRUN=1`。未実行の 1 件は静的の項目で、別の回で流しています)。A6-15 と A6-N1 は、同じく測定 3 より前のビルドで、`test/records/A6/net-n1-2026-11-04.md` で合格しました。

まだ確かめていないことは、記録のそれぞれの「確かめていないこと」「未検証・限界」の節にあります。たとえば A6-15 の実プロセスの試験は作業端末の Node で行い、製品の実行体(Electron の Node)での実測はまだです。その Node は送信を実行時に制限する機能を持たないので、送信先の制限は静的検査と実プロセスの記録で確かめています。

## 開発者向け

- 試験: `make test`(Linux の開発用コンテナ)、`make test-app`(作業端末)、失敗の内訳は `make contract-status`。
- ビルド: `make build`(製品)、`make build-test`(試験)。出力は `dist/<product|test>/bundle/<版>/`(版は `VERSION=`、既定 `0.1.0-dev`)。
  `<os>-<arch>/sitate`、`<os>-<arch>/adapters/<kind>/<name>/`、ソースのアーカイブ `sitate-<版>-src.tar.gz`、SBOM `sitate-<版>.spdx.json`(SPDX 2.3)。

- 試験用の保管先: `make test-env-up NAME=<WP> [KIND=fake]`、`make test-env-down NAME=<WP>`。接続先と資格情報は `test/env/.run/<NAME>/env`(git 管理外)。
