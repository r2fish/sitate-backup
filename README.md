# Sitate-backup

**IT 担当者のいない職場に、会話で始められ、戻せることまで確かめるバックアップ**

> IT 担当者のいない事業所でも、Claude のエージェントとの会話だけで、守りたいデータを選び、初回バックアップと別のサーバーへの復元テストまで辿り着ける。エージェントが乗っ取られても、バックアップは消せない。

Claude には、聞く・調べる・提案する・説明するをさせ、鍵を見る・消す・実行するはさせない。

大会のテーマ「本来、誰にでも届くべきものを」に対して、バックアップと、それが戻せることの確かめを選びました。

作り手は障がい者支援施設の支援職員(IT 担当ではない)で、職員約 50 名が使う職場の業務アプリを Claude Code で作って VPS で運用しており、その職員が携帯から出す申請は、アプリの DB にしかありません。最初は、バックアップは取れば済むと思っていました。ランサムウェアでデータを取り出せなくなったニュースを見て、取るだけでは済まないと考えました。この危機感が、このプロジェクトの動機です。

## 審査員に見てもらう道

審査員の方には、動画と画面の記録で見ていただくことを想定しています。

- 動画: (提出のときにここへリンクを置きます)。製品を映す場面は、受入試験と同じ試験ビルドと合成データの環境で録りました。
  - アプリの入力とクリックは、受入試験の自動の操作役(ドライバ)が入れたもので、人の手の速さではありません。待ち時間は編集で切っています。
  - エージェントの応答は、実物の LLM のものです(LLM へはドライバの中継を通して送ります)。
  - サーバーはすべて作業端末の上のコンテナです。通知の受け手も試験のコンテナで、実物のメールやチャットではありません。危険な操作を拒む場面の保管先は、B2 ではなく試験用の S3 互換の保管先です。
  - 試験ビルドは、使い捨ての署名鍵、試験の時計、接続先の読み替え(試験の環境のコンテナに届くため)を使います。
  - リカバリーフレーズの語は、使い捨ての環境のものですが、ぼかしています。
- ドライバの記録: 受入試験で、エージェントとの会話による導入を最初から最後まで通した記録(会話・道具の呼び出し・結果の JSONL)です。公開用に縮めて識別子を伏せ字にしたものを `test/acceptance/records/` に置き(縮め方は `test/records/A7/shrink-2026-11-05.md`)、試験ごとの判定は `test/records/` に置きます。

審査員の API キーは求めません。この製品は、利用者が自分で用意した LLM API キーでエージェントを動かします。キーを使うと、その持ち主に API の請求が発生します。また、キーは秘密の値なので、審査のために預かる形にしたくありません。試験で使ったキーとバックアップの保管先の鍵は、開発者が自分の端末で扱いました。記録には残していません(記録を入れる前に、その値で検索して一致が 0 件であることを確かめています)。

| A2 | エージェントによる導入(手順書の手順 1〜13。変種を変えて 3 回。台本と環境の作り方は同じ) | 提出するビルドの測定 4: 3 回中 3 回合格。各回、中身で数えた問い 4、分からないまま答えを求めた問い 0、人の作業 4(H1〜H4)(`test/records/A2/m4.md` の「集計」)。ただし、合格の基準の 1 点(推奨の案に「分からなければこの案でよい」と明示する文を求めるか)の読み方は、測定の結果を見た後に決めました。字面どおりに明示の文を求めると、測定 4 も測定 3 も 3 回中 0 回です(`test/records/A2/m4.md` の「境目の判定」の 4)。基準の文言は次の版で直します。前のビルドの値: 測定 3 は 3 回中 3 回(`test/records/A2/m3.md`)。測定 3 には無効にした回が 2 つあります。1 つは、ドライバの取り違えで台本の答えが届かなかった 3 回目で、これを不合格に数えると 3 回中 2 回です。もう 1 つは、使用済みのバケットで流した 2 回目で、回ごとに新しいバケットを使う規則により無効にしました。その前のビルドの測定 2 は 3 回中 1 回(`test/records/A2/m2.md`) |

### 精度の出し方

次の 5 つは最初からあった設計ではなく、失敗のたびに足していったものです。足すかどうかを決めたのは人、形にしたのは Claude です。

1. **役割を別の起動に分け、実装とレビューは別のモデルにする。** 起草とレビュー、実装とレビュー、レビューと監査は必ず別の起動にしました。実装は sonnet、レビューは opus です(起草とレビューはどちらも opus で、起動が別です)。同じ文脈で書いて点検すると、同じ思い込みで通るためです。
2. **「絶対に」の規則は指示でなくフックにする。** 例外を許さない規則は、人と AI の注意に任せず、フックが機械的に拒む形にしました(拒むものは下の機能の表)。
3. **緑を証拠にしない。** 規則として、承認・秘密・送信の制限などの規則の試験は、規則を 1 か所壊した変異で赤になることを確かめてから完了にし、欠陥の修正は修正前のコードで新しい試験が落ちた記録を残し、skip を合格に数えず、既知の欠陥は試験を消さずに赤のまま残して理由を書く、と定めました。実際に行った範囲: 変異は WP の受け入れの記録にあります(【日 7 に入れる: 記録のある WP の数・変異の件数・生存の件数】。例は `test/records/fix-db/acceptance.md` の「監督の再実行と変異」)。修正前の赤の記録は一部の WP だけで、変異で代えた WP もあります。【日 7 に入れる: 既知の欠陥を赤のまま残した実例の件数。無ければこの文を消す】
4. **文書どうしの食い違いを機械で落とす。** 設計の文書(このリポジトリの外。公開していません)を直すたびに、1 か所を直しても同じことを言う他の場所が古いまま残る食い違いが続いたので、作り手が求め、Claude が commit の前に機械で落とす検査を書きました。その後、過去の指摘(【日 7 に入れる: 要素の数】件)を分類すると、この型が【日 7 に入れる: 件数】件で最も多く、分類をもとに検査を 3 つ足し、レビューの点検表も分類から作りました。
5. **決めたことを追記だけで残し、採らなかった案も書く。** 決定記録は番号付きの追記だけで、覆すときは新しい番号を起こします。期間中は監督を設計と製品の 2 つのセッションに分けました。製品の監督が実装で見つけた仕様の食い違いを申し送り(`test/records/U0-core/handoff-to-design.md`)に書いて設計の監督へ知らせ(初日は作り手が貼って運び、2 日目からはセッションどうしが直接知らせる)、設計の監督が裁定して仕様書の版を上げ、製品の監督へ写しました。裁定には、前に別起動のレビューを通したもの、急ぐので機械の検査だけで返して後からまとめてレビューを通したもの、機械の検査だけのものがあります(数は上の表)。

### きっかけ(求めたこと → 形になったもの)

### 報告を信じさせない

- 証拠: 実装担当の報告もレビューの結論も証拠にしません。証拠は、試験ログの集計行の逐語、ログの日時と `git diff --stat` の一致、差分、実測の記録だけです。完了の報告は、完了条件ごとの試験の名前、試験の結果の逐語、修正前のコードでの赤の記録、変異の記録、確かめていない項目の一覧、の 5 つの形で出させます。「全件通った」だけの報告は受け付けず、走らせられなかった試験は「未検証」と書かせます。
- レビュー: ログの日時・`git diff --stat`・試験の結果の逐語で確かめさせ、推論だけで「直った」と結論させません。報告は「確認した観点」と「していない観点」を別の節に分け、赤は 1 件ずつ分類させます。設計の文書のレビューには、過去の指摘の分類から起こした点検表 10 項目を使い、項目ごとに確かめた範囲と確かめていない範囲を報告させます。
- 監査: 完了条件ごとに充足・未充足・証拠不足の 3 値で判定させ、証拠不足を充足に数えません。最終の判定は、監督が最終の作業ツリーで試験を自分で 1 回流し直してから行います(WP ごとの受け入れで行い、全体の受け入れ監査は 7 日目)。
- 実例(測った値): 監査の予行(3 日目)では、完了条件 300 件を充足 117・未充足 20・証拠不足 143・範囲外 20 に分けました。証拠不足の多く(104 件)は完了条件と試験名の対応表の欠けで、7 日目の監査で初めて穴が見つかることを避けるための予行です(`test/records/schedule/day3-midpoint-2026-11-04.md`)。契約の骨格を相手にした契約試験では、判定の行 494 行のうち失敗より手前で実行が届いたのは 8 行(1.6%)で、骨格での赤は試験の品質の根拠にならないと分かり、主経路を先に通す形に変えました(`test/records/U0-core/acceptance.md`)。【日 7 に入れる: レビューの差し戻しの回数、監査で証拠不足から充足に変わった件数。取れなければこの文を消す】
- 設計の側: 期間前から、このリポジトリの外で、独立レビューの記録【日 7 に入れる: 本数】本、決定記録【日 7 に入れる: 件数】件を残しました。

## 作りながら変えたこと

期間中に、試験と測定で見つかったことから製品の形を変えました。製品に関わるものを挙げます。記録はそれぞれの行の置き場にあります。

### 1. エージェントの問いの出し方

- 最初の案: 規則ファイルに「問いの文は疑問符で終える」と書いていました。
- 変えた理由: A2 の測定 1 の 1 回目のやり直しで、エージェントが 2 つの問いをまとめて聞き、文末を「教えてください。」で終えたり、問いの後に説明を続けたりしました。試験用ドライバはこれを問いと数えず続行を返し続け、入力の回数の上限で止まりました。
- 今の形: 規則ファイルに問いの出し方の節を足しました(疑問符で終える、1 回に 1 つ、発話の最後の文にする、手順の順を守る、開始時の入力の前に道具を呼ばない)。直してから測定 1 を測り直しました。直した後の 1 回目では、ドライバの記録の `question_not_last`(問いが最後の文でない)と `multi_question`(1 回に複数の問い)はどちらも 0 でした。この回は手順 11 で止まり、不合格に数えました(次の 2)。
- 記録: `test/records/A2/m1-pre.md`

### 2. PostgreSQL の対象の取得の要求の形

- 最初の案: 核は、どの種別の対象にも同じ形の取得の要求(ファイルのパスの欄を持つ)を組んでいました。
- 変えた理由: A2 の測定 1 の 1 回目で、PostgreSQL の対象の要求が空のパスで組まれ、要求の検証で落ちて内部エラーになりました。主経路の試験は DB のクラスタを対象から外していて、DB の取得を実物の核で通した試験がありませんでした。対象の失敗には原因の欄も次の行動も無く、エージェントは原因を言えずに止まりました。
- 今の形: 要求の形を種別ごとに分け、PostgreSQL の対象はパスを持たない形にしました。対象の失敗は原因(`detail`)と次の行動(`next`)の欄を持ちます。DB の対象を実物の環境で取り、復元先にダンプが届く試験 `TestStageDB` を足しました。
- 記録: `test/records/A2/m1-pre.md`、`test/records/fix-db/acceptance.md`

### 3. 確定の前の定義の検査

- 最初の案: 定義の検査(`def validate`)は、参照名が解決できないと止まりました。
- 変えた理由: 保管先の鍵の参照名は手順 5、復元先の参照名は手順 9 で初めて置かれます。手順 4 の検査は必ず止まり、導入が進みませんでした。
- 今の形: 確定(`seal`)の前は、これらの参照名が未解決でも止まらず、結果の `pending_refs[]` に載せます。手順 5・9 で解決します。
- 記録: `test/records/U0-core/handoff-to-design.md` の 31 節

### 4. 手順 4 の順(通知先の登録と定義の検査)

- 最初の案: 手順 4 は、定義の検査、通知先の登録の順でした。
- 変えた理由: 定義の通知先は参照名で、登録の前は解決できず、検査で止まりました。

### 5. 承認鍵をエージェントに渡させない

- 最初の案: 初期化の道具(`sitate_init`)の定義に承認鍵の欄があり、エージェントの入力のまま核へ渡っていました。

### 6. 初期化の前の保管先の確認

### 11. アプリが作る封筒の整形

- 最初の案: アプリが作る封筒(引用の照合の通知など)は、核の結果と同じ整形を通らずに LLM API へ送られていました。
- 変えた理由: 送った欄の検査(A7)で、測定 1〜3 の記録の、アプリの引用の照合の区画の `/result` が送る欄の表の外の欄として不合格になりました。値は `null` で、値の漏れはありませんでした。
- 今の形: アプリが作る封筒も同じ整形を通します。この直しを入れた提出するビルドの測定 4 では、3 回とも送る欄の表に無い欄は 0 でした。前のビルドの不合格は、前のビルドの値として記録に残しています。
- 記録: `test/records/A7/2026-11-04.md` の (ii) の (a)、`test/records/A2/m4.md`

このほか、LLM API へ送る欄の表(アプリのデータ)を仕様の表と照合し、欠けていた 2 つの欄を足しました(`test/records/U0-core/send-fields-1.2.23.md`)。結果の次の行動の欄名(`next` の要素の名前)は、仕様の書き損じを直し、封筒の `next` と同じ欄(`argv`・`requires_human`・`requires_approval`・`why`)に揃えました。

## 無料で自前に組むツールと比べて

比べる相手は、無料で自前に組むツール(restic・BorgBackup・Kopia)に限ります。相手の欄は 2026 年 10 月の調査です。比較の条件(対象・保持・支援の範囲)が揃わないので、事実だけを並べます。導入の手順の数は数え方が違うので並べません。この製品の欄は、受入試験で確かめたものだけです。

| 項目 | 無料で自前に組むツール(2026 年 10 月の調査) | この製品(確かめた試験) |
|---|---|---|
| 戻せることの確認 | 別のサーバーへ戻して確かめる復元テストは、3 つとも手で行う。復元を証明する仕組みは、restic は調べた範囲で見つからず、BorgBackup(borgmatic)は部分的(展開のドライラン、元ファイルとの比較)、Kopia は部分的(構造と存在の確認) | 別のサーバーへ実際に戻して確かめ、署名した合格の記録を出す(A2 の手順 12)。定期の実行と世代の整理のタイマーは、導入の会話の中で登録される(A2 の手順 13 の `doctor` の `timers_registered`) |

この製品は、導入と運用の会話を AI のエージェントに任せる作りです。比べた 3 つのツールの調査では、この点は項目にしていません。危険な操作が人の承認と時間の遅れを経ないと起きないことは A6、秘密の値がモデルに送られないことは A7 で確かめました。

LLM API キーは、エージェントのプロセスが持ちます(起動の後に渡されます)。「鍵を見せない」と言うのは、保管先・サーバーの鍵と承認鍵の値がモデルの文脈に入らないことです。

提出するビルド(測定 4 と同じ試験ビルド)の A6 は、CLI の回を受入試験の環境で流し直して合格し(`TestA6CLI`)、静的検査も合格し、実物の LLM の注入文の回と合わせた判定は `A6 summary PASS=20 FAIL=0 UNRUN=2` です(`test/records/A6/real-m4-2026-11-05.md`)。前のビルドの値: CLI の回は、測定 3 より前のビルドで、実物の LLM API と保管先には何も送らない試験ビルドと受入試験の環境で行い、12 項目が合格しました(`test/records/A6/cli-2026-11-04.md` の集計行 `A6 summary PASS=12 FAIL=0 UNRUN=1`。未実行の 1 件は静的の項目で、別の回で流しています)。A6-15 と A6-N1 は、同じく測定 3 より前のビルドで、`test/records/A6/net-n1-2026-11-04.md` で合格しました。

まだ確かめていないことは、記録のそれぞれの「確かめていないこと」「未検証・限界」の節にあります。たとえば A6-15 の実プロセスの試験は作業端末の Node で行い、製品の実行体(Electron の Node)での実測はまだです。その Node は送信を実行時に制限する機能を持たないので、送信先の制限は静的検査と実プロセスの記録で確かめています。
