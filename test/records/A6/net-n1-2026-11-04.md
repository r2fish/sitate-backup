## (a) 静的検査(A6-15a)

- 依存の木(入口 `src/agent/entry.ts` から import をたどった自前 + node_modules)に http・https・http2・net・tls・dgram・undici・ws の import が 0 件。WebSocket・XMLHttpRequest・EventSource・`globalThis.fetch` の参照が 0 件。
- 自前のソースで識別子 `fetch` が現れるのは入口の `makeGuardedFetch(fetch, ...)` の 2 箇所(通常と試験用ビルドの口)だけ。その `fetch` は `new Anthropic({ fetch: withUsageReport(makeGuardedFetch(...)) })` の形で SDK に明示して渡す。
- 依存の木で識別子 `fetch` を持つファイルは SDK の既知の 10 件に限る(新しい経路が入れば赤)。大域の `fetch` への既定は SDK の `internal/shims.js` の 1 箇所で、`client.js` は渡された `fetch` を先に使う。
- 束ねた成果物(esbuild の出力。製品と試験用の両方)に、送信の経路のモジュールの require が 0 件、組み込みモジュールの require は fs・fs/promises・os・child_process・path・crypto・stream・util・readline だけ。

## (b)(c) 実プロセス(A6-15b/c)

エージェントのプロセスを製品と同じ実行引数(`agentExecArgv`: `--permission --allow-fs-read=<束ねた成果物の置き場>`)で起動し、標準入力で IPC のメッセージを送る。起動前の読み込み(`--require`)で `fetch`・`WebSocket`・`net.Socket#connect`・`tls.connect`・`dgram.createSocket`・`http(s).request` の呼び出しを標準エラーに TRACE として記録する。

1. 通常の会話: 呼び出しは `fetch` 2 回と LLM の口への接続 1 回だけ。WebSocket・tls・dgram・http.request は 0 件。別のホストの口へは 0 回。
2. LLM の口が別のホストへ 302 で転送(攻撃者の口の想定): `ready` にならず `failure`(`id` = null、`code` = `LLM_PROVIDER_ERROR`)で終わり、別のホストの口は 0 回、別のホストへの接続は 0 件。
3. 実プロセスの guarded fetch(別のホスト、同じホストの別のポート、別名 127.0.0.2、`localhost`、不正な URL): 5 件すべて `EGRESS_DENIED` で失敗し、標準エラー(プロセスの記録)に `EGRESS_DENIED <送り先>` が 5 行残る。口への送信は 200 で通る。別のホストの口は 0 回。
4. 禁じた経路(同じプロセス): `typeof XMLHttpRequest` = `undefined`、子プロセスの起動・ファイルの書き込み・許可の外の読み取りが `ERR_ACCESS_DENIED`。

## 未検証・限界(監督へ)

1. 製品の実行体(Electron 45 の Node 24)での実測は未検証。試験は作業端末の Node v26 で、`--allow-net` を知る版では Node 24 に合わせて `--allow-net` を付け、送信を制限しない状態で走らせている。
2. 実行時に口の外の経路が「無いか失敗する」を literal に満たすのは、子プロセス・書き込み・許可の外の読み取り・`XMLHttpRequest` だけ。`fetch`・`WebSocket`・`net` はプロセスの中に残る(Electron の Node に `--allow-net` が無いため、実行時の遮断が無い)。代わりに (a) の静的検査と、実プロセスで全呼び出しの送り先が LLM の口だけであることの記録で担保している。大域の `fetch`・`WebSocket` を実行時に無効にする手(入口で退避して消す)は製品の変更で、この記録では行っていない。
3. 製品は `EGRESS_DENIED` をプロセスの記録に自分では書かない。口の外への送信が SDK の中で起きると、主プロセスへ返る `failure` の `code` は `LLM_PROVIDER_ERROR` になり、拒否の理由を区別できない。この記録の `EGRESS_DENIED` の行は試験用のプローブが書いたもの(実プロセスの guarded fetch の例外の型 `EgressDeniedError` を見て書く)。
4. 本番の LLM API(`api.anthropic.com`)への実際の接続は試験していない(禁止)。送り先の origin の検査は `LLM_API_BASE_URL` を許可に渡した同じ関数を、127.0.0.1 の口で確かめたもの。
