# 主経路の第 3 段の記録(2026-11-03)

- 対象: 仕様書 1.2.10 を基に作業(監督の途中の連絡で 1.2.11・作業指示書 1.0.20、D-0163 を追加)。台本は `test/mainpath/stage3_*_test.go` の `TestStage3MainPath`。
- 実行: `bash test/env/bin/accept-env.sh up mp3`、`LOCK_DEFAULT_DAYS=90 make test-env-up NAME=mp3` の後に `make test-mainpath STAGE=3 NAME=mp3`。試し直しは環境を作り直した。
- 結果: `--- PASS: TestStage3MainPath (56.36s)` / `ok  github.com/r2fish/sitate-backup/test/mainpath  56.374s`。

## 通したもの(実物の sitate、gate 経由)

1. seal: `notify set`(hook の Webhook)→ `notify test`(確認語は hook の記録から読む)→ `propose seal` → 違う確認語の承認は `NOTIFY_PROOF_MISMATCH` で状態不変 → 承認(台本が承認鍵を持ち、記録から `canonical_hash` を自分で RFC 8785 で計算し直して署名)→ `apply`。`sealed` が真、`state` が `applied`、`/etc/sitate/sitate.yaml` が書かれ、`change.proposed`・`change.approved`・`change.applied` が hook に届いた。seal の遅延は 0(提案の `delay_hours`=0、仕様 3.6 の表)。遅延があれば共有の時刻を進める分岐を書いたが、通っていない。
2. seal の後の backup を、元データを変えて 2 回(`list` に両方、世代は別)。各 backup の直後に元データから照合の行を計算。
3. seal の後の `restore-test`: `restore_ok`・`keyring_ok`・`def_copy_ok`・`config_copy_ok` がすべて真、直近の世代、`teardown.remaining` が `[]`、`restore_test.passed` が hook に届いた。
4. 世代ごとの別のサーバーへの復元: seal の前の 1 世代と seal の後の 2 世代を dest で `restore` し、元データと同じ計算(種別・モード・サイズ・更新時刻・リンク先・SHA-256)で一致。保存済みマニフェストは使っていない。
5. seal の後に gate 経由で `restore-dest enroll`・`source enroll`・`init-storage`・`notify set` が `APPROVAL_REQUIRED`(終了 4)で、`secrets/`・`def/` が不変。sitate ユーザーの書き込み鍵(秘密ファイルにある鍵と同じことを確認)で、最新の世代のマニフェスト 1 つとチャンク 3 つのロック中の版の `DeleteVersion` と保持の短縮が MinIO に `STORAGE_DENIED` で拒否され、版は読めたまま。
6. 失敗の経路: dest の専用ユーザーの作業場所 `~/.sitate/run` を root 所有・0500 にして `restore-test` を実行 → 失敗(`ADAPTER_ERROR`、`adapter:ssh-host:SESSION_EXISTS`)、`restore_test.failed`(`error_code` が封筒と一致)が hook に届き、`status.last_restore_test.ok`=false・`consecutive_failures`=1。直すと同じ月に合格する。
   - この形を選んだ理由: 保管先のロック中の版は破壊できず(Compliance)、復元先の核は台本が差し替えられない(登録後に核が毎回置く)。復元先の環境の障害は台本が入れられる。**読み出しを始める前の失敗**(仕様 3.5 の表の 3〜6)で、予約を消費しない。読み出し後の失敗(`RESTORE_MISMATCH` など)と、処理が残る(`TEARDOWN_UNVERIFIED`)形は未検証。
   - `SESSION_EXISTS` は作業ディレクトリを作れない失敗の写像で、名前が実態と合わない(下の見つけたもの)。

## 復元先に平文が残らないこと

dest は登録の後、受信がバックアップサーバーだけになる。台本は **バックアップサーバーへ入った SSH の中の直接 TCP**(`ssh.Client.Dial`)で dest の管理アカウントに入り(`host.via`)、restore-test の後に次を確かめた: 直近の世代の元データに入れた目印の文字列を含むファイルが `/`(proc・sys を除く)に 0、作業ディレクトリ `~/.sitate/run` が空、専用ユーザーの処理は podman の pause だけ(ps の表示が `podman`)。使い捨て暗号化領域の鍵と平文はメモリ上にあるため、メモリの中までは見ていない。

## メモリのピークと MLOCK(D-0163)

- ピーク(`/proc/<pid>/status` の VmHWM を 0.02 秒ごとに読み、プロセスごとの最後の値の最大。comm=`sitate` のプロセス。合成データ 約 2.6 MB・56 ファイル):

| 実行 | ホスト | VmHWM 最大(kB) |
|---|---|---|
| backup(seal の後 1 回目) | backup | 73620 |
| backup(seal の後 2 回目) | backup | 74068 |
| restore-test の核 | backup | 465928 |
| restore-test の復元先の核(`restore`) | dest | 23972 |

  実行ごとに数 % ずれる(別の実行で backup 40036〜74100、restore-test の backup 側 448056〜468312 kB)。データが小さい環境の値で、大きなデータの値ではない。
- bootstrap の段 (5) に、`/etc/security/limits.d/sitate.conf` の `sitate soft/hard memlock unlimited` と、sshd が PAM(`UsePAM yes`、`pam_limits.so`)を使うことの検査を足した(`memlockLimitsScript`。アプリの `bootstrap.ts` は wp/mp-mlock)。受入環境の sshd は PAM を使っており、環境を直す必要は無かった。
- 実効値: gate 経由で動く核の `/proc/<pid>/limits` の Max locked memory は、足した状態で `unlimited unlimited`、足さない状態(`test/env/.run/accept-<NAME>/no-mlock` を置く)で `2615861248 2615861248`(コンテナの既定。約 2.4 GiB)。gate 経由の封筒 38 回の警告の集計は、どちらも空。
- **「足す前に MLOCK_FAILED が毎回載る」ことは確かめられなかった**: この作業ツリーの核は mlock を呼ばず、`MLOCK_FAILED` を出す箇所が無い(`internal/contract/codes_table.go` の定義のみ)。受入環境の既定の memlock も大きい。台本は封筒の `MLOCK_FAILED` の回数を数え、limits.d を置いた状態では 0 を要求する(核が mlock を足した後で効く)。上限が低い環境での再現は未検証。

## 代役(台本が代わりに行ったもの)

## 見つけたもの

実装の誤り(直した。変えた製品コードは下の一覧):

- D1: `notify test` の要求が `adapter/notify.json` のスキーマに通らない(`facts_notify_test` は `change_id` を必須とするが、核が付けていなかった)。アダプタの実行器は起動の前に検査して落とすため、実物の `notify test` は必ず `adapter_failed` だった。`internal/state/notifier.go`(`"change_id": nil`)、赤→緑の試験 `TestTestNotifierRequestPassesAdapterSchema`。
- D2: `change.proposed`・`change.approved`・`change.applied` の facts に `expired_reason`(必須)が無い。`internal/approval/propose.go`・`approve.go`・`apply_record.go` に `"expired_reason": nil`。試験は台本(hook に届くこと)。**wp/mp-rest の担当範囲の `internal/approval/` を 3 行触った**。
- D3: seal の前は承認済みの定義が無く、`Recorder.Emit` の宛先が空になり、seal の提案・承認の通知がどこにも送られなかった(遅延中の配送成功の要件が成り立たない)。`internal/state/emit.go` で、承認済みの定義が無ければ候補の `notify.to` を使う。赤→緑の試験 `TestEmitUsesCandidateRecipientsBeforeSeal`。

仕様の穴(報告のみ。推測で埋めていない):

- G1: seal の `apply` が書く `/etc/sitate/sitate.yaml` の置き場を sitate が書ける形にする手順が、bootstrap(仕様 3.7、`bootstrap.ts`)に無い。
- G2: 承認前の変更への `apply --id` が `SIGNATURE_INVALID`(`CHANGE_STATE_INVALID` が自然)を返す。何も変わらないが、`change.failed`(critical)が出るかは未確認。
- G3: ssh-host が作業ディレクトリを作れない失敗が `SESSION_EXISTS` と報告される(`scripts_scratch.go` の `mkdir "$w" || exit 3`)。
- G4: 復元で `symlink` の `mtime_ns` を戻さない(仕様 3.1.2.4 は `file`・`dir` だけ戻す)。台本の照合は symlink の更新時刻を比べない(第 2 段の元データに symlink が無く、今まで見えなかった)。
- G5: seal の後の `notify-add`・`notify-change` の試験通知(`approval.issueChangeProofs`)の `facts.change_id` は提案の change_id であるべきだが、核の `TestNotifier` は null を送る(D1 の直しは notify test の null のみ)。この経路は未検証。
