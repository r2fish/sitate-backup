## 1 偽の LLM の A2

- lo(環境 nclo): 終了コード 0。手順 1〜13 すべて合格。ただし偽の LLM の定義は対象が `/srv/shopapp` のファイルだけ(app/test/e2e/fake-agent.ts の definitionOf)で DB の対象を含まない。このため実物の回で出る DB の取得(手順 11 の postgresql 対象)を通っていない。実物の回との差。
- nocluster(環境 ncnc): 終了コード 1「台本に無い人の作業で止まった(同じ依頼の繰り返しで、道具を呼ばない)」。止まった所は手順 8。合格した手順は 1〜7、9〜13 で、手順 8 だけ未合格。`source check` は ok:true だが `actionable` に `db_cluster` ポート 5433 が残った。偽の LLM の定義が `declined` に `postgresql_cluster: 5432` を固定で書いていて、変種 nocluster の 2 つ目のクラスタ(5433)を断らないため。実物の LLM なら Q4 の答え(使っていない方は対象外)で 5433 を断る前提で、偽の LLM 側の限界(製品の誤りではない)。手順 13 の後、全手順が揃わないまま続けて「ご依頼のとおり進めました。」を繰り返して打ち切られた。

## 2 読み取り(直さない)

- (a) 食い違いの疑い。precheck.go の needsInit は "bucket check" を含み init の前に NOT_INITIALIZED を返す。仕様 3.8 の導入手順は 5(init-storage → bucket check)が 6(init)より前で、3.1.2 の bucket check の行も seal の前は保存した候補で動くと書き、init を前提にしない。needsInit が仕様と合わないので、エージェントが手順 5 の bucket check を呼べば実物の 1 回目と同じく init を先に呼ばされる。init-storage 自体は needsInit に無く、内部で bucket check の試験を行う。
- (b) 書かれていない。sitate_source_enroll.json の host に description も形の例も無い。install.md の手順 8 は `source enroll --admin-ref source-admin` と書き --host を含まない。形 ssh://<user>@<host> が出るのは install.md 手順 4 の `source survey` の行(ポート無し)と復元先の定義例(:22 付き)だけ。ssh://<user>@<host>:<port> の形は enroll の道具の説明にも手順書にも無い。
- (c) 書かれていない。sitate_init_storage.json の adapter は型だけ(説明・既定なし)。install.md の手順 2・5 の init-storage の例は --adapter を付けていない。precheck.go の必須は endpoint・bucket・prefix・adapter で、省くと ARG_INVALID(missing)になる。手順書の例と必須が食い違う。
- (d) 要確認。seal 後の status.estimate は cost_ceiling_yen 0・monthly_jpy null・over_ceiling null・warnings 空(nclo の記録で確認、MinIO の保管先)。仕様 4.1 の既定は 3000 で、価格表に無い保管先なら PRICE_UNKNOWN の警告と over_ceiling null(3.1.2.8)。null は仕様どおりだが、ceiling 0(定義に書かなければ 3000 の既定のはず)と PRICE_UNKNOWN 警告が出ていない点は期待と違う可能性がある。実物の B2 の回で ceiling と価格表の行を見る。
- (e) 当たっている。driver-server.ts の 51 行は `buf += d.toString("utf8")` で、sock に setEncoding も StringDecoder も無い。チャンクの境目で多バイト文字が割れると U+FFFD になり得る(ca0dc93 の「受信の UTF-8」はこの箇所を直していない)。
- (f) 当たる見込み。internal/acquire/run_target.go の targetSpec は postgresql の対象で spec.path に t.Files(空)を入れ、取得アダプタの要求の schema(acquire.json、path は anypath で 1 文字以上)に反するため adapters/acquire/postgresql が INTERNAL(reason: request)を返す。有効な見本(testdata の acquire-request-first.json)は path に `/var/run/postgresql` を入れている。lo は DB(docstore)を対象にする答え(「顧客のデータベース」)なので手順 11 で止まる見込み。nocluster は 5433 のクラスタに DB の対象は無いが、元サーバーには 5432 の DB(shopdb など)があり、Q4 の答え「会計ソフトのデータ」が DB を指して対象に入れば同じ INTERNAL で止まる。通るのは DB の対象を入れない場合だけ。
- 2 回目の前に `app/src/testing/driver-server.ts` の受信の UTF-8 を直した(`StringDecoder`。試験の口で測定の対象外。設計の監督の裁定)。試験ビルドを作り直して再署名した。
